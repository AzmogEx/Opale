# Consignes du projet Opale

- Toute fonctionnalité ajoutée, modifiée ou supprimée doit être documentée dans `docs/` dans le même changement que le code. Mettre à jour sa fiche dans `docs/fonctionnalites/`, l'index `docs/README.md` et, si nécessaire, les contrats API, le modèle de données et l'exploitation. Cette règle vaut aussi pour la sécurité, les réglages, les intégrations et les changements d'interface.
- Une fiche décrit le besoin, le parcours utilisateur, les données et calculs, les API et sources concernées, la configuration, les erreurs/limites et la vérification reproductible. Distinguer ce qui est implémenté, testé avec des données synthétiques et validé avec un fournisseur/appareil réel. Ne jamais documenter une promesse comme une fonctionnalité livrée.
- Le catalogue `docs/catalogue.json` associe explicitement chaque route HTTP et chaque écran/composant à une fiche. Pour un nouveau point d'entrée, compléter le catalogue puis lancer `python3 scripts/check_docs.py --write` et `python3 scripts/check_docs.py`. Ne pas masquer une absence de documentation par une exclusion.
- Le backend de l'application est imposé : `https://opale.vaycode.com`. Aucun choix de serveur, préférence stockée ou paramètre public ne doit modifier cette destination. Les exceptions de recette sont confinées au simulateur iOS Debug en boucle locale et aux interceptions du navigateur de test ; elles ne doivent pas exister sur iPhone ou dans le web livré.
- Ne jamais placer de secret ou de donnée personnelle dans la documentation, les fixtures ou les logs de recette. Utiliser une API et une base jetables pour les tests qui écrivent des données.
- Un push sur `main` déclenche automatiquement la production Coolify. Exécuter les contrôles adaptés avant de pousser ; documenter les migrations et besoins de configuration. Préserver les données existantes.
